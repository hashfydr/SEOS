Chapter 1

Introduction
1.1

Background and Context

Software engineering is usually taught as a sequence of separate topics: requirements
elicitation, user stories, UML and entityrelationship (ER) modeling, architecture,
API design, testing and documentation [Som15, PM19]. Each topic is assessed with
its own artefact, and students typically produce those artefacts in dierent tools 
requirements in a word processor, class diagrams in a drawing tool, schemas in a
database designer, API contracts in Swagger, and reports in Markdown or Word.
In real projects, however, these artefacts are tightly coupled. Adding a single eld
to an entity should change the database schema, the request and response schemas of
the API, and the relevant sections of the Software Requirements Specication (SRS)
and Software Design Document (SDD). When the artefacts live in unrelated tools,
keeping them consistent is a manual, error-prone task and the reasoning that connects
one artefact to the next is rarely made explicit.

SEOS (Software Engineering Operating System) is an AI-powered workspace that
takes a natural-language software idea and guides it through the complete engineering
pipeline  from requirements to documented, deployable design  while explaining why each engineering decision was made. The platform is intentionally domainagnostic: the same workow applies to a food-delivery platform, a hospital system,
a college application or a banking system.

In this report the running case study

is FoodDash, an on-demand food delivery platform generated end-to-end inside the
current SEOS prototype.

1.1.1

Problem Statement

Students and small teams building software projects face three distinct challenges:
1.

Artefact Fragmentation

: Requirements, diagrams, schemas, APIs and doc-

uments are produced in separate tools with no single source of truth. A change
in one artefact must be manually propagated to every downstream artefact, and
inconsistencies accumulate silently.

2.

Black-Box AI Generation

: General-purpose AI assistants can produce UML

diagrams or API specications on request, but each output is an isolated text
blob.

They neither maintain relationships between artefacts nor justify their

choices with established software engineering principles, so learners copy outputs
without understanding them.
3.

Missing Learning Feedback

:

Existing tools focus on producing artefacts,

not on building understanding. Learners receive no signal about which concepts
they have encountered, which stages they have completed, or why a particular
architecture or normal form was chosen.

1.2

Pro ject Ob jectives

The core objectives of SEOS are formulated under the SMART (Specic, Measurable,
Achievable, Relevant, Time-bound) framework for a three-person team over a sixmonth timeline:
1.

Objective 1: Connected Engineering Model

:

Implement a single rela-

tional Project Model in which requirements, actors, user stories, entities, relationships, architecture, API endpoints and documents are stored as linked
objects with explicit trace links, so that a downstream artefact can always be
traced to its origin.
2.

Objective 2: Validated AI Generation Pipeline

:

Build an end-to-end

pipeline (Idea → Requirements → User Stories → UML/ER → Architecture →
OpenAPI → SRS/SDD/README) in which every LLM response is returned
as structured JSON, validated against a schema, and approved by the user
before it is persisted. Generated OpenAPI documents must be importable into
Swagger or Postman without manual correction.
3.

Objective 3: Grounded Explanations and Learning Analytics

: Ground

engineering explanations in a curated software engineering knowledge base using Retrieval-Augmented Generation (RAG) [Lew20] over PostgreSQL with

pgvector, and track learner progress through a Learning Dashboard. At least
ve external users should complete the full workow by Month 6.

1. AI Requirements Engineer
Rather than generating a long document from a vague prompt, the requirements
engine rst identies ambiguity and asks targeted clarication questions about actors, goals, system boundaries, constraints and assumptions. The backend sends the
idea plus conversation context to the LLM, which must return JSON conforming to
a predened RequirementSet schema. Each requirement carries a type (Functional
or Non-Functional), a priority (Critical, High, Medium) and a status (Draft or Approved).

Invalid responses are sent back to the LLM with the validation errors in

a bounded repair loop (at most two retries) before the user is asked to clarify. For
the FoodDash case study the engine produced six requirements (four functional, two
non-functional), two of which have been approved (Figure 3.2).
The dynamic interaction between the student, frontend, backend, LLM gateway,
schema validator and database is detailed in the Sequence Diagram in Figure 2.4. It
traces three phases: idea submission with the validation/repair loop, transactional
persistence of draft requirements together with their trace links, and the approval
step that advances the project's pipeline_stage to user stories.

2. User Story Generator
Approved requirements are transformed into user stories of the form As a <role>,

I want <goal> so that <benet> , each with acceptance criteria. Every story stores
a trace link to its source requirement, so the user can always see where a story
originated. In FoodDash, the four core requirements were converted into four user
stories with acceptance criteria.

3. Interactive UML & ER Designer
Entities, attributes and relationships are extracted from approved requirements and
stories into the Project Model and rendered on a React Flow canvas (Figure 3.3).
The diagram is not a static image: each node maps to a model object (Diagram Node

↔ Model Object ↔ Database ).

Users can open an entity and edit its elds, data

types, primary/foreign-key ags and methods (Figure 3.4). The FoodDash ER model
contains six entities  User, Order, Restaurant, Payment, Delivery and MenuItem.

Module 2: Secondary Features

1. AI Architecture Designer
Once requirements and models exist, the architecture engine analyses scale, functional
boundaries, coupling and operational complexity, and recommends an architectural
style (layered, modular monolith or microservices) together with its trade-os. The
emphasis is on reasoning rather than on producing a diagram. For FoodDash  which
needs real-time updates across three consumers (customer app, restaurant dashboard,
driver app) and independent scaling of order processing and delivery tracking  SEOS
recommended an Event-Driven Microservices architecture with Apache Kafka as the
message backbone, listing eight components and explicit pros and cons (Figure 3.5).
The recommendation is labelled AI-Generated · Grounded via RAG.

2. RAG Explanation Layer
SEOS grounds its explanations in a curated knowledge base covering requirements
engineering, UML, design principles, architecture, database design, API design, testing and documentation.

in pgvector; at query time the top-k chunks are retrieved by cosine similarity and

3. API Designer and Living Documentation
REST endpoints and schemas are derived from entities, relationships and user stories
and serialised as an OpenAPI 3.1 document [OAS21] (Figure 3.6). The documentation
engine then generates an SRS (following the structure of IEEE 830 [IEEE98]), an SDD
and a README directly from the current model. Because each document stores the

model_version it was generated from, SEOS can detect when a document is out of
date and regenerate it  the idea of living documentation (Figure 3.7).

Conclusion
4.1

Summary of Work

SEOS has been designed and partially implemented as an AI-powered Software Engineering Operating System that carries a software idea through requirements, user
stories, UML/ER modeling, architecture, API design and documentation inside one
workspace. The prototype demonstrates the full workspace, a working requirements
and user-story pipeline, an interactive ER canvas with entity editing, an architecture
recommendation with trade-os, an OpenAPI generator, document generation and a
Learning Dashboard, all on the FoodDash case study.

4.2



Key Findings

A Shared Model Matters More Than Generation:

The most valuable

property of SEOS is not that it generates artefacts, but that they are stored
as linked objects.

The inconsistencies found in the prototype appear exactly

where a view is not yet derived from the model.



Structured Output Makes AI Reliable Enough to Persist:

Requiring

schema-valid JSON with a bounded repair loop, followed by human approval,
keeps malformed or contradictory LLM output out of the Project Model.



Explanations Turn a Tool into a Learning Environment:

Pairing each

decision (e.g. choosing event-driven microservices) with its trade-os and grounded
references gives learners the why, not just the what.
